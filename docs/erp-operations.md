# 운영 절차 — 매일 · 매주 · 사고가 났을 때

> 이 문서는 **시스템을 쓰는 절차**입니다. 오픈 전 준비는 `erp-open.md`,
> 무엇을 왜 그렇게 만들었는지는 `erp-devlog.md` 에 있습니다.

---

## 0. 하루의 흐름 — 한 건이 지나가는 길

```
요청 → 필수값 채우기 → 승인·반려 → 집행대기 → 실제 입출금 확인 → 잔액 대사 → 마감
 슬랙      검수함·원장      대기함      지급 순서        지급 순서        현금흐름표   마감
```

**승인과 지급은 다른 일입니다.** 승인은 「나가도 된다」이고, 입출금 확인은
「실제로 나갔다」입니다. 승인만 해 두고 확인을 안 하면 집행대기에 그대로
남아 있습니다 — 그게 맞습니다. 통장에서 빠진 것을 보고 확인하십시오.

## 0-1. 오픈 첫날 — 첫 화면의 「오픈 전 점검」부터

**종합 현황** 맨 위에 점검 결과가 뜹니다. **「막는 것」이 하나라도 있으면
그것부터 처리하십시오** — 이대로 쓰면 화면은 멀쩡해 보이고 숫자만 틀립니다.

| 막는 것                     | 왜 위험한가                                                                        | 어디서                                      |
| --------------------------- | ---------------------------------------------------------------------------------- | ------------------------------------------- |
| 「오늘」이 과거에 박혀 있음 | 현금흐름표의 「오늘」, 채권 연령, 지급 기한, 부족액이 **전부 그 날 기준**이 됩니다 | 기준값 → `today_override` 를 비웁니다       |
| 보유현금 없음               | 부족액·런웨이가 안 섭니다                                                          | 기준값 → `cash_on_hand`                     |
| 급여 실액 없음              | 런웨이 3종이 전부 「계산 불가」                                                    | 기준값 → `payroll_monthly_actual` (월 총액) |

> `today_override` 는 시드 기본값이 **2026-08-27** 입니다. 데모 데이터를 그
> 날짜로 보이게 하려던 값인데 운영에 그대로 남아 있으면 시스템 전체가 그 날을
> 오늘로 여깁니다. **오픈 전에 반드시 비우십시오.**

## 1. 매일 (15분)

### ① 검수함 — 슬랙에서 온 것 (5분)

**수집 검수함** 화면.

| 보이는 것      | 할 일                                            |
| -------------- | ------------------------------------------------ |
| 대기           | 내용을 보고 **원장 적재**를 누릅니다             |
| 파싱 실패      | 원문을 보고 **직접 입력**합니다. 버리지 마십시오 |
| 자동 수집 상태 | 막힌 것이 있으면 여기 뜹니다 (아래 4장)          |

- 수집 자체는 **매시 정각에 자동으로** 돕니다. 화면을 열어 둘 필요가 없습니다.
- 실비 정산에는 주민등록번호가 들어 있습니다. 화면에는 `******-*******` 로만
  보이고, 「주민번호 보기」 + 비밀번호 재입력으로만 열리며 **열람이 기록됩니다.**

### ② 승인 대기함 — 내 차례인 것 (5분)

**승인 대기** 화면. 역할별로 나뉘어 있습니다 —
대표 결재 대기 / 재무 검토 대기 / 리더 확인 대기.

승인이 막히는 이유는 넷뿐이고, 화면이 어느 것인지 말해 줍니다.

| 막힌 이유     | 누가 푸나   |
| ------------- | ----------- |
| 금액 미정     | 재무·담당자 |
| 계정과목 없음 | 재무        |
| 증빙 없음     | 담당자      |
| 한도 초과     | 상위 승인자 |

> **본인이 손댄 건은 본인이 승인할 수 없습니다.** 우회로가 없습니다.

### ③ 입출금 확인 — 실제로 나간 것 (5분)

**지급 순서** 화면 → 건마다 **「입출금 확인」**.

- **이 버튼은 이체를 실행하지 않습니다.** 통장·카드 내역을 보고, 이미 움직인
  것을 기록하는 것입니다.
- **부분 지급**이면 나간 금액만 넣으십시오. 남은 금액이 집행대기에 남습니다.
- **은행 거래번호**를 같이 넣으면 같은 출금을 두 건에 확인하는 사고를 시스템이
  막아 줍니다. 되도록 넣으십시오.
- 잘못 눌렀으면 **취소**할 수 있습니다. 줄은 남고 사유가 기록됩니다.

대표·부대표·재무만 할 수 있습니다 — 통장을 여는 역할입니다.

## 2. 잔액 대사 (매일 또는 주 1회)

**현금흐름표**에는 잔액이 **네 가지** 있습니다. 섞어 보면 안 됩니다.

| 이름          | 무엇인가                                    | 은행과 맞춰 보나 |
| ------------- | ------------------------------------------- | ---------------- |
| **종료**      | **승인된 건**으로 이은 계산 잔액            | 아니오           |
| **대사 잔액** | **실제 입출금이 확인된 것만**으로 이은 잔액 | **예 — 이것만**  |
| 시트 잔액     | 시트에 사람이 적어 둔 값                    | 참고용           |
| 보유현금      | 기준값 화면에서 사람이 통장 보고 적는 값    | 입력값           |

**대사 방법** — 인터넷뱅킹 잔액과 **대사 잔액**을 비교합니다.

| 차이가 나면               | 원인                                                           |
| ------------------------- | -------------------------------------------------------------- |
| 대사 잔액이 **크다**      | 나간 것을 아직 확인 안 했습니다                                |
| 대사 잔액이 **작다**      | 원장에 없는 출금이 있습니다 — 건을 만드십시오                  |
| 종료와 대사 잔액이 다르다 | 정상입니다 — 그 차이가 **승인은 났지만 아직 안 나간 돈**입니다 |

### 계에서 빠지는 것 두 가지

- **법인카드 사용분** — 긁은 날 통장은 그대로입니다. 카드대금 결제일에 한 번
  나갑니다. 둘 다 세면 같은 돈이 두 번 빠집니다.
- **내부 계좌이체** — 우리 계좌끼리 옮긴 것이라 보유현금 총액이 변하지
  않습니다. **집행원장에서 직접 두 건을 만들지 마십시오** — 반드시
  「내부 계좌이체」로 기록해야 짝이 맞습니다.

둘 다 계에서는 빠지지만 **금액이 따로 표시됩니다.** 숨기지 않습니다.

## 3. 시트와 원장이 다를 때

시트는 실무에서 계속 씁니다. 원장에는 이미 운영 데이터가 들어가 있습니다.

> ⚠️ **「시트를 최종본으로 다시 깔기」는 오픈 후에 쓰지 마십시오.**
> 그 사이 원장에서 고친 것과 슬랙에서 올라온 것이 **전부 날아갑니다.**
> 검수함도 함께 비워집니다.

대신 **시트 이관 → 「시트와 원장의 차이 보기」**. 읽기만 하고 아무것도
지우지 않습니다.

| 종류         | 할 일                                                      |
| ------------ | ---------------------------------------------------------- |
| 시트에만     | 원장에 직접 넣습니다                                       |
| 원장에만     | 시트에서 지워진 건입니다 — 취소할 건인지 확인              |
| 금액 다름    | 어느 쪽이 맞는지 확인. 승인된 건이면 **수정본**을 만듭니다 |
| 방향 다름    | **먼저 보십시오** — 손익 부호가 걸린 문제입니다            |
| 시트 안 중복 | 같은 날 같은 항목이 두 번 — 둘 다 맞는지 확인              |

> 한쪽 금액이 비어 있는 것은 차이가 아니라 **아직 모르는 것**이라 목록에
> 올라오지 않습니다 (원칙 8).

## 4. 막혔을 때 — 자동 수집

**수집 검수함 → 「자동 수집 상태」** 카드가 무엇이 막혔는지 말해 줍니다.

| 표시                   | 뜻                   | 할 일                     |
| ---------------------- | -------------------- | ------------------------- |
| 막힌 것 없이 돌고 있음 | 정상                 | 없음                      |
| 속도 제한              | 슬랙이 잠시 조입니다 | 없음 — 자동으로 다시 시도 |
| **사람이 처리해야 함** | 잔액·키·권한 부족    | 아래대로 처리             |

**사람이 처리해야 하는 것**은 재시도로 풀리지 않습니다.

| 이유                     | 처리                                           |
| ------------------------ | ---------------------------------------------- |
| Anthropic 잔액 부족      | console.anthropic.com 에서 충전                |
| `ANTHROPIC_API_KEY` 없음 | Vercel 환경변수에 넣고 재배포                  |
| `SLACK_BOT_TOKEN` 없음   | 슬랙 앱에서 발급 → Vercel 에 넣고 재배포       |
| `files:read` 권한 없음   | 슬랙 앱 OAuth & Permissions → 추가 → Reinstall |

> 읽지 못한 파일은 **목록으로 남습니다.** 성공으로 처리하지 않습니다.

## 4-1. 알림이 안 갈 때

**알림** 화면의 **「도착 못 함」** 타일을 보십시오. 0 이 아니면 **알림함에는
떠 있지만 아무도 못 받은** 것입니다 — 「읽지 않음」과 다릅니다.

| 표시                      | 뜻                                        | 할 일                |
| ------------------------- | ----------------------------------------- | -------------------- |
| 도착 못 함 0건            | 정상                                      | 없음                 |
| 도착 못 함 N건            | 발송 실패 — 다음 크론에서 다시 시도합니다 | 이유를 보십시오      |
| 「재시도를 포기했습니다」 | 3번 실패                                  | 원인을 고쳐야 합니다 |

| 실패 이유           | 처리                                                |
| ------------------- | --------------------------------------------------- |
| `channel_not_found` | `SLACK_NOTIFY_CHANNEL` 채널 ID 확인                 |
| `not_in_channel`    | 그 채널에서 `/invite @디노 경영관리`                |
| `invalid_auth`      | `SLACK_BOT_TOKEN` 재발급 후 재배포                  |
| 도착지 「미정」     | `SLACK_NOTIFY_CHANNEL` 미설정 — 알림함에만 쌓입니다 |

> 원인을 고친 뒤에는 **새 알림부터** 갑니다. 포기한 건은 알림함에서 직접
> 확인하십시오.

### 「지금 보내는 중입니다」가 보일 때

화면 조회와 매시 크론이 **같은 발송 경로**를 씁니다. 두 곳이 같은 순간에
같은 알림을 집지 못하도록, 보내기 **전에** DB 한 문장으로 선점합니다. 그
선점은 잠금이 아니라 **2분짜리 임대**입니다.

그래서 한쪽이 보내는 동안 다른 쪽에는 그 알림이 「지금 보내는 중」으로
보입니다. **이것은 실패가 아닙니다** — 새로고침하면 「갔다」나 「도착 못 함」
으로 바뀝니다.

### 이 방식이 막지 못하는 것 — 알아 두셔야 합니다

임대는 **중복을 줄이지만 없애지는 못합니다.** 슬랙 `chat.postMessage` 에는
「같은 요청을 두 번 받아도 한 번만 처리한다」고 표시할 방법이 없기 때문입니다.
남는 구멍은 둘입니다.

| 언제                                               | 무슨 일이                           | 결과                                             |
| -------------------------------------------------- | ----------------------------------- | ------------------------------------------------ |
| 슬랙이 받은 **뒤** 프로세스가 죽음 (배포·타임아웃) | 「보냈다」를 기록하기 전에 끊긴다   | 2분 뒤 다음 번이 **같은 알림을 한 번 더** 보낸다 |
| 슬랙 응답이 **유실** (네트워크)                    | 도착했는지 알 수 없다 — 실패로 센다 | 다음 시도에서 **한 번 더** 갈 수 있다            |

즉 이 시스템의 알림은 **「최소 한 번」**이지 「정확히 한 번」이 아닙니다.
같은 경보가 드물게 두 번 오면 장애가 아니라 위 두 경우입니다. 반대 방향
(아예 안 감)은 **「도착 못 함」 타일이 잡습니다** — 그쪽을 우선해서 보십시오.

재시도는 **3번까지**입니다. 채널 ID 가 틀린 상태로 무한히 두드리면 크론이
매시 같은 벽에 부딪히고 실패 이유만 덮어쓰기 때문입니다.

## 5. 월 마감

1. **판정 대기 0건** — 금액·항목명이 다 채워져야 합니다
2. **입출금 확인** — 그 달 승인 건의 실제 지급이 다 확인돼야 합니다
3. **잔액 대사** — 대사 잔액과 은행 잔액이 맞아야 합니다
4. 마감 화면에서 **마감 요청**(재무) → **마감 승인**(대표)

> 마감된 기간은 수정할 수 없습니다. 고치려면 마감을 풀어야 하고, 푼 기록이
> 남습니다.

## 6. 사고가 났을 때

| 상황                          | 조치                                                                 |
| ----------------------------- | -------------------------------------------------------------------- |
| 잘못 승인했다                 | 건에서 **취소** — 취소본이 생기고 원본은 남습니다 (원칙 9)           |
| 잘못 입출금 확인했다          | 확인 이력에서 **취소** + 사유. 줄은 남습니다                         |
| 같은 지출이 두 번 들어왔다    | 하나를 **취소**하고 사유에 「중복」. 지우지 마십시오                 |
| 내부이체를 지출로 잘못 넣었다 | 그 건을 취소하고 **「내부 계좌이체」로 다시** 기록                   |
| 화면 숫자가 이상하다          | 현금흐름표에서 **네 가지 잔액**을 각각 확인 — 어느 것이 이상한지부터 |
| 슬랙이 아무것도 안 가져온다   | 「자동 수집 상태」의 막힌 이유를 먼저 보십시오                       |
| 배포가 깨졌다                 | Vercel → Deployments → 직전 배포 **Promote to Production**           |
| DB 가 이상하다                | 아래 7장                                                             |

**하지 말아야 할 것**

- ❌ 「시트를 최종본으로 다시 깔기」 (오픈 후) — 운영 데이터가 날아갑니다
- ❌ DB 에서 직접 행을 지우는 것 — 원칙 9. 취소로 처리하십시오
- ❌ 판정 대기 건의 금액을 0 으로 채워 넣는 것 — 합계가 조용히 틀어집니다

## 7. 백업과 복구

**Neon 은 PITR(시점 복구)을 제공합니다.** 백업은 자동이지만,
**복구가 되는지는 해 봐야 압니다.**

### 복구 리허설 (오픈 전 1회 · 이후 분기 1회)

1. Neon 콘솔 → **Branches** → `main` 에서 **Create branch**
2. 복구 시점을 **어제**로 지정 → 새 브랜치 생성
3. **복구 전에 기준값을 적어 둡니다** — 지금 운영 화면에서 보이는
   원장 건수와 입출금 확인 합계, 그리고 복구 기준 시각. 이것 없이는
   「완전히 복구됐는지」를 판정할 방법이 없습니다

4. 그 브랜치의 연결 문자열로 검증 스크립트를 돌립니다

   ```
   node scripts/verify-restore.mjs "<복구 브랜치 연결 문자열>" \
     --as-of=2026-09-20T09:00:00+09:00 --entries=61 --settled-total=12345678
   ```

   표 22개 · 나중에 생긴 칸 · **마이그레이션 장부** · 원장 건수 · 입출금 확인
   합계 · 감사로그 마지막 기록을 봅니다. **읽기만 하고 아무것도 쓰지 않습니다.**

   | 끝나는 값 | 뜻                                                          | 할 일                         |
   | --------- | ----------------------------------------------------------- | ----------------------------- |
   | `0`       | 스키마 · 장부 · 기준값이 전부 맞습니다                      | 통과                          |
   | `3`       | **읽히지만 완전복구는 미검증** (기준값을 안 줬습니다)       | 기준값을 주고 다시 돌리십시오 |
   | `1`       | 스키마가 덜 따라왔거나, 장부가 안 맞거나, 기준값과 다릅니다 | 복구 시점을 다시 잡으십시오   |
   | `2`       | 연결 문자열이 없거나 운영과 같습니다                        | 인자를 고치십시오             |

   > **「원장이 비어 있지 않다」는 완전복구가 아닙니다.** 기준값을 주지 않으면
   > 스크립트는 거기를 **미검증**이라고 말하고 `3` 으로 끝납니다. 통과로
   > 세지 마십시오.

   > **마이그레이션 장부를 봅니다.** 표가 다 있어 보여도 나중에 생긴 칸
   > (`erp_notification.leaseUntil`, `erp_user.buCode` 같은 것)이 없으면 지금
   > 배포가 그 복구본 위에서 첫 조회부터 터집니다. 장부 대조가 그걸 잡습니다.

5. 확인이 끝나면 **그 브랜치를 지웁니다** — 남겨 두면 어느 것이 운영인지
   헷갈립니다

> 스크립트는 연결 문자열이 운영 `DATABASE_URL` 과 같으면 **거부합니다.**
> 복구본이 아니라 운영을 확인하고 「복구됩니다」라고 결론 내리는 것이
> 이 리허설이 막으려는 바로 그 사고이기 때문입니다.

> ⚠️ **운영 DB 를 복구 대상으로 삼지 마십시오.** 반드시 **새 브랜치**로
> 복구해 확인하고, 운영은 건드리지 않습니다.

### 실제로 복구해야 할 때

1. 먼저 **언제까지가 정상인지** 정합니다 (감사로그가 도움이 됩니다)
2. 그 시점으로 **새 브랜치**를 만들어 내용을 확인합니다 —
   `verify-restore.mjs` 를 **기준값과 함께** 돌려 `0` 이 나와야 합니다.
   `3`(미검증)으로는 연결을 바꾸지 마십시오
3. 확인이 끝난 뒤에만 연결을 그쪽으로 바꿉니다
4. 바꾼 뒤 **그 사이에 들어온 것**을 다시 넣어야 합니다 — 슬랙 수집은
   자동으로 다시 가져오지만, 사람이 손으로 넣은 것은 다시 넣어야 합니다

## 8. 전환과 복귀

### 시트 → 시스템 (전환)

- 시트는 **읽기 전용으로 바꾸지 마십시오.** 검증이 끝날 때까지 양쪽을
  같이 씁니다
- 매일 「시트와 원장의 차이 보기」로 대조합니다
- 차이가 **1주일 연속 0건**이면 시트 입력을 멈추고 시스템만 씁니다
- 그때 시트를 읽기 전용으로 돌립니다 (지우지 않습니다 — 이력입니다)

### 시스템 → 시트 (복귀)

시스템을 못 쓰게 됐을 때.

1. **현금흐름표 → 내보내기** — 일별·월별 전부
2. **집행원장 → 내보내기** — 전 기간
3. 두 파일을 시트에 붙여 넣고 그때부터 시트로 운영합니다
4. 복귀한 시점을 기록해 두십시오 — 다시 돌아올 때 그 시점부터 맞춥니다

> 외부열람 역할은 **내보내기가 막혀 있습니다.** 복귀는 대표·재무가 합니다.
