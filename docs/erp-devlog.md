## 12회차 — 로그인 실패 원인을 감추지 않게

**요청**

> (배포 미리보기에서 로그인 시도) 서버에 연결하지 못했습니다 — 라고만 나옴

**무엇이 문제였나**

이 문구는 제가 쓴 `catch` 한 줄이었습니다. 그런데 `response.json()`은 응답이 JSON이 아니면
그 자리에서 예외를 던지므로, **404 안내 페이지든 500 오류 텍스트든 전부 같은 catch로 떨어져**
「연결하지 못했습니다」로 뭉뚱그려졌습니다. 실제로는 연결은 됐고 서버가 다른 답을 준 것인데,
화면만 봐서는 배포 문제인지 네트워크 문제인지 비밀번호 문제인지 구분할 수 없었습니다.

**고친 것** — 본문을 먼저 글자로 받고, JSON 파싱은 따로 시도합니다.

| 실제 상황            | 이전                       | 지금                                                                         |
| -------------------- | -------------------------- | ---------------------------------------------------------------------------- |
| 함수 미배포 (404)    | 서버에 연결하지 못했습니다 | 로그인 API를 찾을 수 없습니다 (404). 배포에 서버 함수가 포함되지 않았습니다. |
| 함수 실행 실패 (500) | 〃                         | 서버가 예상과 다른 응답을 보냈습니다 (HTTP 500). FUNCTION_INVOCATION_FAILED  |
| 진짜 네트워크 실패   | 〃                         | 서버에 연결하지 못했습니다 — (원인 메시지)                                   |
| 비밀번호 오류 (401)  | 정상 표시                  | 그대로                                                                       |

로그인 수단 조회(`/api/auth/methods`)도 같이 고쳤습니다. 이전에는 조회가 실패해도 조용히
두 수단을 다 그려서 **아무 문제 없어 보였는데**, 이 조회가 실패했다면 로그인 요청도 실패할
가능성이 높습니다. 이제 실패 사실을 화면에 남깁니다.

**판단이 갈린 곳**

| 무엇                           | 어떻게 정했나       | 왜                                                                                  |
| ------------------------------ | ------------------- | ----------------------------------------------------------------------------------- |
| 오류 본문을 화면에 노출할까    | **앞 120자만 노출** | 배포 오류는 대부분 첫 줄에 원인이 있음. 전체를 뿌리면 스택 트레이스가 사용자에게 감 |
| 수단 조회 실패를 조용히 넘길까 | 넘기지 않음         | 「조용한 폴백」이 이번 진단을 늦춘 원인. 실패는 보이는 편이 낫다                    |
| 401 문구                       | 그대로 유지         | 계정 존재 여부를 감추는 설계(11회차)를 깨면 안 됨                                   |

**검증**

- 자동 테스트 113건 통과 · `tsc --noEmit` 무오류 · 빌드 성공
- 실제 브라우저에서 세 가지 실패를 각각 흉내내어 **서로 다른 문구가 나오는 것** 확인
  (함수 404 · 함수 500 비JSON · 정상 로그인)
- `api/auth/password.ts` · `api/auth/methods.ts` · `api/trpc/[trpc].ts` 를 esbuild로 각각 번들해
  `@shared/*` 별칭이 서버리스 번들에서도 풀리는 것 확인 (배포 실패 원인 후보에서 제외)

## 13회차 — 배포된 서버 함수가 전부 죽어 있었다

**증상**
`/api/auth/methods` 직접 호출 → `500 FUNCTION_INVOCATION_FAILED`.
로컬은 멀쩡, 번들도 성공, 모듈을 직접 실행해도 200. **배포에서만 죽었습니다.**

**원인 — export 형태**

| 파일                                                                             | 형태                                         | 배포     |
| -------------------------------------------------------------------------------- | -------------------------------------------- | -------- |
| `google/start.ts` · `google/callback.ts` · `erp/evidence.ts` · `slack/events.ts` | `export async function GET(...)`             | 정상     |
| `auth/logout.ts` · `auth/methods.ts` · `auth/password.ts` · `trpc/[trpc].ts`     | `export { handler as GET, handler as POST }` | **죽음** |

Vercel 런타임은 파일을 **정적으로 훑어** 어떤 HTTP 메서드를 다루는지 정합니다.
별칭 재export 는 실행하면 분명히 존재하는 export 인데도 그 탐지에 잡히지 않아,
런타임이 다룰 메서드를 못 찾고 호출 단계에서 죽습니다.

경계선이 정확히 이 두 형태를 가릅니다 — 같은 배포 안에서 선언형 4개는 살아 있고
별칭형 4개만 죽었습니다. `api/trpc` 도 여기 포함되므로 **경영관리 시스템의 모든 데이터
요청이 처음부터 실패하고 있었습니다.** 화면이 로그인 카드를 보여준 것도 그래서였습니다
(로그인이 안 된 게 아니라 조회 자체가 실패한 것).

**고친 것** — 8개 파일 전부 선언형으로 통일 (`363890a` 다음 커밋).

**재발 방지** — `server/apiHandlers.test.ts`.
`api/` 아래 모든 파일을 읽어 별칭 재export 를 금지하고 선언형 export 를 강제합니다.

## 14회차 — 배포에서만 죽던 진짜 원인 (확정)

**증상** `/api/auth/methods` → `500 FUNCTION_INVOCATION_FAILED`. 로컬은 전부 정상.

**13회차의 진단은 틀렸다**
export 형태(`export { handler as GET }`)를 원인으로 지목했으나 고쳐도 그대로였다.
`FUNCTION_INVOCATION_FAILED` 는 **런타임이 함수를 찾아서 실행했다**는 뜻이므로
탐지 실패가 아니라 **모듈이 뜨는 순간 죽는 것**이었다. 추측을 멈추고 환경을 재현했다.

**재현 방법 (이게 결정적이었다)**

```
esbuild <모든 .ts> --outdir=... --format=esm --platform=node   # --bundle 없음
echo '{"type":"module"}' > out/package.json
node -e 'import("./out/api/auth/methods.js")'
```

`--bundle` 을 빼는 것이 핵심이다. Vercel 은 파일별 트랜스파일만 하고 Node ESM 으로 실행한다.
이 상태로 돌리자 로컬에서 배포와 **똑같은 오류**가 재현됐다.

**진짜 원인 — Node ESM 이 지원하지 않는 import 형태 3종**

| 형태                 | 예                           | Node ESM                     |
| -------------------- | ---------------------------- | ---------------------------- |
| 확장자 없는 상대경로 | `from "./session"`           | `ERR_MODULE_NOT_FOUND`       |
| 폴더 import          | `from "../erp"` · `from "."` | `ERR_UNSUPPORTED_DIR_IMPORT` |
| tsconfig 별칭        | `from "@shared/const"`       | 런타임에 존재하지 않음       |

셋 다 vite · tsx · esbuild 번들은 알아서 풀어준다. **번들러가 감춰 온 부채**였고,
번들하지 않는 환경에 처음 올린 순간 한꺼번에 터졌다.

**고친 범위** — `api` · `server` · `shared` · `drizzle` 의 relative import 168곳,
`@shared/*` 별칭 16개 파일, 점 하나짜리 폴더 import 2곳 (`from "."`).
`api/**/*` 를 tsconfig `include` 에 추가 (여태 배포용 함수는 타입 검사도 안 받고 있었다).

**재발 방지 — `server/vercelRuntime.test.ts`**
번들 없이 트랜스파일 → 진짜 Node 자식 프로세스에서 모든 `api/*` 를 import 한다.
**vitest 의 모듈 로더를 거치면 안 된다** — 그 로더가 경로를 대신 풀어주어 재현이 깨진다.
확장자를 일부러 하나 지워 테스트가 실제로 잡는지 확인했다 (파일명과 오류코드까지 지목함).

**판단이 갈린 곳**

| 무엇                                | 어떻게 정했나          | 왜                                                                                            |
| ----------------------------------- | ---------------------- | --------------------------------------------------------------------------------------------- |
| 확장자를 붙일까, 번들 설정을 바꿀까 | **확장자를 붙인다**    | 번들 여부와 무관하게 항상 옳다. esbuild·vite·tsx 모두 `.js` → `.ts` 를 풀어주므로 손해가 없다 |

## 15회차 — 로그인 수단이 하나도 없을 때

**또 나온 「필드는 있는데 저장이 안 되던 것」**

`incomeType` · `withheldAmount` · `principalAmount` 는 Entry 타입에만 있었다.
DB 컬럼도, API 입력도, 폼도 없었다 — 시드와 테스트에서만 값이 들어갔고 DB 를
한 번 돌면 사라진다. `bankAccount` 는 `createEntry` 가 `null` 로 고정하고 있었다.
전표 `journalNo` 와 거래처 `incomeType` 은 스키마에만 있고 마이그레이션이 없었다.

원인은 같다 — **타입에 필드를 추가하는 것과 그 필드가 저장되는 것은 다른 일이다.**
이번에는 도메인 → DB 컬럼(0006 마이그레이션) → API 입력 → 폼까지 네 자리를
한 번에 확인했다. 앞으로 필드를 추가할 때 이 네 자리를 같이 본다.

**검증** — 자동 테스트 300건 · 타입체크 통과 · 프로덕션 빌드 통과 ·
마이그레이션 `0006_rich_the_call.sql` 생성 (이전 회차의 누락분 5건 포함).

## 앞으로 이 문서를 쓰는 법

새 작업을 할 때마다 아래 형식으로 회차를 **추가**합니다. 지우지 않습니다.

```
## N회차 — 제목
**요청** (원문 그대로)
**만든 것** (커밋 해시 + 목록)
**판단이 갈린 곳** (표: 무엇 / 어떻게 정했나 / 왜)
**검증** (테스트 수 · 실제 확인한 것)
```

「판단이 갈린 곳」이 이 문서의 핵심입니다. 코드는 무엇을 하는지 말해주지만
**왜 그렇게 정했는지**는 말해주지 않습니다.
