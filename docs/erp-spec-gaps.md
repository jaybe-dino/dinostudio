## A. 사양서에 없어서 추가한 것 (4건) — 없으면 §9.2 수치가 재현되지 않습니다

### A1. `entry.amount_candidate` — 적요칸 후보 금액

§9.2 본문은 `ON : amount=null 건은 합계에서 빠지되 "n건 제외 중" 경고 표시`라고 적었지만,
같은 절과 T6이 제시한 수치는 그 반대입니다.

| 토글 | 사양서 P0 부족액 | 필요액     |
| ---- | ---------------- | ---------- |
| OFF  | 여유 17,650,000  | 350,000    |
| ON   | −272,110         | 18,272,110 |

차이 17,922,110 = **12,614,300 + 5,307,810** — EX-260827-02 · EX-260827-03의 *적요칸 금액*입니다.
즉 ON은 판정 대기 건을 빼는 것이 아니라 **적요칸 금액으로 포함**합니다.

그래서 `amount`(확정 금액)와 별도로 `amount_candidate`(적요칸 후보)를 두었습니다.
후보 금액은 현금 현황의 필요액에서만 쓰이고 **현금흐름 계 · 손익 · 전표에는 절대 들어가지 않습니다.**
단위가 불명한 값(80 · 350 · 1,200)은 후보로도 승격하지 않고 null로 둡니다 (원칙 8).

> 확인 필요 — §9.2의 ON 설명 문장을 수치에 맞게 고칠지, 아니면 수치를 문장에 맞출지.
> 문장을 따르면 P0 부족액이 −272,110이 아니라 여유 17,650,000이 되고, T3 ③ · T6이 동시에 깨집니다.

### A2. `entry.paid_at` — 이미 집행이 끝난 날

§9.2의 필요액은 `Σ entry[status ∈ {confirmed, pending}, out, priority_eff ≤ L]`입니다.
시드에 그대로 적용하면 P0+P1 필요액이 52,572,110이 나오는데 사양서는 39,072,110입니다.
차이 13,500,000은 **이미 나간 3건**입니다.

| 코드         | 항목               | 금액      |
| ------------ | ------------------ | --------- |
| EX-260826-05 | 연장 보증료 (8120) | 2,000,000 |
| EX-260827-05 | 상환 (2210)        | 5,000,000 |
| EX-260827-06 | 상환 (2210)        | 6,500,000 |

P2 단계도 같습니다 — 이미 집행된 EX-260826-06(8,800,000) · EX-260826-08(770,000)을 빼면
사양서의 90,957,110이 정확히 나옵니다.

필요액은 「앞으로 막아야 할 돈」이므로 이미 나간 확정 건을 제외해야 맞습니다. §6.2에 그 구분이 없어
`paid_at`을 추가했습니다.

### A3. `setting.cash_requirement_horizon` — 소요 지평

위 계산에서도 승인 대기 2건이 남습니다.

| 코드                           | 발생일        | 금액      | 사양서 필요액 포함 |
| ------------------------------ | ------------- | --------- | ------------------ |
| EX-260831-01~04 · EX-260901-01 | 08/31 ~ 09/01 | —         | 포함               |
| EX-260825-01                   | **09/05**     | 8,800,000 | 미포함             |
| EX-260930-01                   | **09/30**     | 6,600,000 | 미포함             |

지평을 `2026-09-01`로 두면 세 단계 필요액이 18,272,110 / 39,072,110 / 90,957,110으로 **전부 일치**합니다.
임시값으로 setting에 넣었습니다 — 실제 기준(이번 주 / 이번 달 / D+N)을 정해 주십시오.

### A4. `entry.is_personal` — 개인이 식별되는 인건비 건

원칙 10은 「개인별 급여는 어느 화면에도 표시하지 않는다. 총액만」이고, §13.1은 대표조차 급여를
`R(총액)`으로만 봅니다. 그런데 시드에는 개인 건(EX-260827-02 대표·본인 / EX-260827-03 본인)과
전사 건(EX-260831-04 8월 급여 전사)이 섞여 있어 구분 없이는 총액만 보여줄 수 없습니다.
`is_personal`로 구분해 응답 단계에서 마스킹합니다 (T10).

## B. 사양서 안에서 서로 어긋나는 것 (5건)

### B1. §9.1 「08/28부터 계산 불가」 → 실제로는 **08/26부터**

미확정 승계 규칙(`판정 대기가 남은 날부터 day_close = null`)을 시드에 그대로 적용하면
08/26에 이미 판정 대기 3건(EX-260826-02 · -03 · -07)이 있어 그 날부터 승계됩니다.
T5의 요구(08/28 이후 전부 null)는 충족하지만 시작점이 이틀 빠릅니다.

규칙대로 구현했고, 차이는 화면과 테스트에 그대로 노출했습니다.
08/26·08/27 판정 대기 건이 실제로는 `cash_date`가 없는 건(아직 나가지 않은 건)이라면 알려 주십시오 —
그러면 사양서 본문과 일치합니다.

### B2. §8.1 마스터 vs §8.2 `autoPriority()` — 6310 지급수수료

§8.1 표는 6310의 기본 우선순위를 **P2**로, §8.2 함수는 같은 계정에 **P3**를 돌려줍니다
(함수의 P2 조건이 `/^5\d{3}$/`이므로).

§6.3이 "자동 판정 3종은 전부 account 테이블 컬럼에서 나온다"고 규정하므로 **마스터 컬럼을 실사용 값**으로
쓰고, 함수는 마스터가 빈 계정의 폴백으로만 씁니다. 계정과목 체계 화면에 두 값이 갈리는 계정을 표시합니다.

### B3. 전표는 3차인데 T1이 1차에서 요구합니다

§6.3은 `journal` / `journal_line`을 3차로 잡았지만, 1차 인수 기준 T1 ⑤는 "전표 1건 자동 생성"입니다.
T1을 통과시키기 위해 1차에 넣었습니다. 차변 합 == 대변 합을 코드와 DB 제약 양쪽에서 막습니다.

### B4. 전표 상대계정이 §8.1에 없습니다 — 1110 · 2120 추가

분개는 상대계정이 있어야 성립합니다. §8.1 마스터에는 보통예금이 없어 두 계정을 추가했습니다.

| 코드 | 계정과목            | 언제                                  |
| ---- | ------------------- | ------------------------------------- |
| 1110 | 보통예금            | 결제수단 = 계좌 · 현금                |
| 2120 | 미지급금 (법인카드) | 결제수단 = 법인카드 · 개인카드 선결제 |

프로토타입 전표 화면도 1110 보통예금을 쓰고 있어 그대로 맞췄습니다. 계정 체계를 확정해 주십시오.

### B5. 보유현금 18,000,000 vs 이관 08/25 종료 3,000,000

일계 7행은 08/25 종료를 3,000,000으로 남기는데(그 행 자체가 "08/26 시작에 맞추기 위한 조정 포함"),
현금 현황의 보유현금은 18,000,000입니다. 15,000,000 차이입니다.

§9.2가 보유현금을 「Σ 계좌 잔액(대사 완료분)」으로 정의하므로 원장 체인과 별개 값으로 보고
setting에 임시값으로 넣고 화면에 **임시 배지**를 붙였습니다. B5(이관 조정 사유)와 같은 뿌리입니다.

## D. 기술 스택 (2건)

### D1. PostgreSQL 필수 → 이 레포는 MySQL입니다

§15는 PostgreSQL을 "대체 없음"으로 적었지만 `dinostudio` 레포는 mysql2 + Drizzle로 운영 중입니다.
사양서가 실제로 요구하는 것은 **정확한 정수 원 · 부동소수 금지**이므로 금액을 전부 `BIGINT`(정수 원)로
잡았습니다. DECIMAL / FLOAT / 소수 연산은 어디에도 없습니다.

Postgres로 옮겨야 한다면 스키마는 `drizzle/erpSchema.ts` 한 파일이라 dialect 교체로 끝납니다.

### D2. 권한 매트릭스가 초안입니다 (G10)

§13.1이 초안이라 역할 자체는 매트릭스대로 구현하고, **사람 → 역할 배정**은 환경변수로 뺐습니다.

```
ERP_ROLE_MAP='{"ceo@dinostudio.kr":"대표","cfo@dinostudio.kr":"재무"}'
```

프로덕션에서는 이 배정이 없으면 접근이 막힙니다(빈 화면이 아니라 "역할이 지정되지 않았습니다").
대표 검토 후 확정되면 `erp_user` 테이블로 옮깁니다.
